# HDP v0.1 — Design (approved 2026-06-12)

Harness Definition Protocol: a vendor-neutral, machine-readable format that **defines** an
LLM-agent harness as the source of truth, compiled by generators to concrete backends, and
**evolved** through a standardized, governed edit interface.

This design was produced in two brainstorm rounds; the second round pressure-tested every
decision against full reads of the relevant literature (see
[docs/literature-review-hdp.md](../../literature-review-hdp.md)).

## Decisions (all approved)

| # | Decision | Choice | Grounding |
|---|---|---|---|
| 1 | Schema identity | **Definitional/generative** — HDP is authored truth; generators compile to backends; the evolution loop edits HDP, not harness files | Survey conclusion: "turning ETCLOVG into a normative framework… is the natural next step"; §9.7(1) calls for an MCP-analogous community spec |
| 2 | Domain model | **ETCLOVG layers** (Execution, Tooling, Context, Lifecycle, Observability, Verification, Governance) with typed components nested inside | ETCLOVG = the field's shared taxonomy (170+ projects mapped); HarnessFix keys flaw diagnosis & repair to it |
| 3 | Content strategy | **Hybrid**: embed declarative text (rules, tool descriptions, skills, memory, policies, verifier contracts); reference executable code (tool impls, middleware) | AHE ablation: declarative layer transfers; Life-Harness: harness transfers across 17 models because it captures environment structure, not model behavior |
| 4 | Document form | **Directory + `hdp.yaml` manifest**, content in per-component files | AHE file-level observability; Meta-Harness filesystem feedback channel (82 files/iter); HarnessFix artifact-level repair |
| 5 | Evolution interface | **Closed operator vocabulary** (`add/update/remove/narrow/gate`) + change-manifest entries carrying HarnessFix-style repair specs and AHE-style falsifiable predictions; `remove` first-class | HarnessFix: constrained ops beat unconstrained edits (15–50% rel.); survey §12.5 adaptive simplification; AHE decision observability |
| 6 | Trace linkage | **Minimal SHOULD-level convention**: runtimes tag trace spans with the responsible `component_id`; no trace format owned | HarnessFix HTIR responsibility facets; survey §12.3 trace-native evaluation |

## Non-decisions / explicit v0.1 exclusions

- Compilers/generators per backend (piece B of the program; NexAU generator is the first target).
- The generalized evolution loop itself (piece C — AHE generalization).
- Handoff contracts for sub-agents (survey §12.4), component conflict declarations, full trace IR.
- Runtime schema mutability — deliberately rejected: versions are frozen snapshots; runtime
  adaptation is *declared component behavior* (Life-Harness shows runtime adaptation needs no
  schema mutation).

## Acknowledged trade-off

Typed decomposition gives up Meta-Harness-style free-form program search (monolithic 100–1000-line
harness programs, "full program rewrites rather than filling in templates"). Mitigation: the
referenced-code escape hatch. Justification: HarnessFix's ablation ("unconstrained edits
significantly underperform") and AHE's attribution machinery, which exists only because of
decomposition.

2. `hdp/schema/hdp.schema.json` — JSON Schema for the manifest
